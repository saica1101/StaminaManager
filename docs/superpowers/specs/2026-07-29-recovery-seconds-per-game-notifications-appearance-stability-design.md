# 回復秒・ゲーム別通知・外観切替安定化 設計仕様

## 1. 文書の位置付け

本書は、既存の
`docs/superpowers/specs/2026-07-25-stamina-manager-design.md` に対する追加仕様である。
回復間隔、残り時間表示、通知条件、外観切替について、本書と既存仕様が競合する場合は
本書を優先する。

対象となる要求は次の4点である。

- スタミナ1回復の間隔を分単位から分＋秒単位へ拡張する。
- 満タン通知を登録ゲームごとに有効・無効化できるようにする。
- 満タンまで1日未満の場合、残り時間を `hh:mm:ss` で表示する。
- SettingsとOverviewの往復を含むテーマ・バックドロップ切替で発生するクラッシュを
  解消する。

## 2. 確定事項

- 回復間隔の入力には、Fluent標準の `NumberBox` を分・秒の2項目で使用する。
- 個別通知の初期値は、既存ゲームと新規ゲームのどちらもONとする。
- Settingsの通知設定はマスター設定とし、実効通知状態は
  `Settingsの通知ON && ゲームの個別通知ON` とする。
- 1日以上の残り時間は現在の `D日 hh:mm` 表示を維持する。
- 1日未満の残り時間は `hh:mm:ss` とする。
- Mica、Acrylic、Blur、Transparent、Solidの5背景は維持する。
- ユーザーが加えた既存UI調整を維持し、関連箇所を最小差分で修正する。

## 3. 回復間隔モデル

### 3.1 保存値

`GameEntry` は既存の `RecoveryMinutes` を維持し、次を追加する。

- `int RecoverySeconds`: 0～59の秒部分。既存データでは0。
- `bool IsNotificationEnabled`: ゲーム別通知。既存データでは `true`。

`GameDraft` にも同じ2項目を追加する。アプリ内部の現行モデルでは両項目を必須とし、
すべての生成箇所で明示する。スキーマ1だけが後述の移行DTOで既定値を補う。

計算に使う回復間隔は常に次の合計秒へ正規化する。

```text
recoveryIntervalSeconds = RecoveryMinutes * 60 + RecoverySeconds
```

自然回復数と全回復時刻は次で求める。

```text
elapsedSeconds = floor(max(0, nowUtc - RecordedAtUtc).TotalSeconds)
recovered = floor(elapsedSeconds / recoveryIntervalSeconds)
fullAtUtc = RecordedAtUtc
            + checked((MaxStamina - BaseStamina)
                      * recoveryIntervalSeconds
                      * TicksPerSecond)
```

秒を含む乗算は `checked` で行い、`DateTimeOffset` の表現範囲を超える場合は従来どおり
入力エラーとして扱う。

### 3.2 入力範囲

- 分: 0～525,600の整数。
- 秒: 0～59の整数。
- 合計回復間隔: 1秒以上、525,600分以下。
- `0分0秒` と `525,600分1秒` は無効。

分・秒のどちらかが非整数、非有限値、範囲外の場合は、対応する入力欄の直下へ
エラーを表示する。合計値のエラーは回復間隔グループの直下へ表示する。

### 3.3 編集時刻の扱い

現在値、最大値、回復分、回復秒のいずれかが変更された場合だけ、保存時刻を新しい
`RecordedAtUtc` とする。ゲーム名、画像、個別通知だけの変更では計測開始時刻を変更しない。

## 4. データ互換性

1分未満の回復間隔や個別通知OFFを旧アプリが誤解釈しないよう、データスキーマを2へ
更新する。

- 読み込みはスキーマ1と2を受け付ける。最初にルートのスキーマ番号を読み、
  スキーマ別DTOへ分岐する。
- スキーマ1は新項目を持たない専用DTOで読み、各ゲームへ
  `RecoverySeconds = 0`、`IsNotificationEnabled = true` を明示的に補って
  スキーマ2へ正規化する。
- スキーマ2は `RecoverySeconds` と `IsNotificationEnabled` を必須項目として読む。
  どちらかが欠落している場合は、既定値で補わず破損データとして扱う。
- 保存はスキーマ2だけを書き出す。
- スキーマ2を旧アプリがスキーマ1として誤読しないよう、バージョン番号を維持しない。
- バックアップのマニフェスト構造は変わらないため、そのスキーマ番号は維持する。
- バックアップ検証はデータスキーマ1と2を受け付け、復元前にスキーマ2へ正規化する。
- `manifest.DataSchemaVersion` と、アーカイブ内データの `SchemaVersion` は必ず一致させる。
  不一致は改ざんまたは破損として拒否する。
- 新規エクスポートはデータスキーマ2を記録する。

プライマリ、回復用コピー、バックアップのすべてで同じ正規化・検証規則を使用する。
未知のスキーマは従来どおり拒否し、既存ファイルを上書きしない。
この規則を重複実装しないよう、スキーマ判定、デシリアライズ、移行、現行モデル検証を
共通のデータコーデックへ集約する。

## 5. ゲーム編集UI

回復間隔は「スタミナが1回復する時間」という1グループ内へ配置する。

- 左側: 分 `NumberBox`。既存の `RecoveryMinutesInput` AutomationIdを維持する。
- 右側: 秒 `NumberBox`。`RecoverySecondsInput` AutomationIdを付与する。
- 狭いダイアログ幅でもラベル、スピンボタン、エラー表示が切れないよう、既存幅に
  合わせた2列グリッドを使用する。
- キーボードのTab順は、分、秒、個別通知、画像選択の順とする。

画像選択の前へ「満タン通知」の `ToggleSwitch` を追加する。

- AutomationIdは `GameNotificationToggle` とする。
- ON/OFF状態を文字でも識別できるようにする。
- 「Settingsの通知がONの場合に、このゲームの満タン通知を受け取ります」と補足する。
- 色だけで状態を伝えない。

## 6. 残り時間表示

`RemainingTimeParts` に秒を追加する。満タン前に `00:00:00` と表示しないよう、
1日未満では残り秒数を切り上げて表示する。

- `remaining <= 0`: `満タン`。
- `0 < remaining < 1日`: `満タンまで hh:mm:ss`。
- `remaining >= 1日`: 従来どおり分単位で切り上げ、
  `満タンまで D日 hh:mm`。

1日未満かどうかの分岐は丸め前の `TimeSpan` で判定する。Overviewカードとコンパクト
表示は同じ分解規則とローカライズ済みリソースを使用する。
`23:59:59.x` は残り秒の切り上げ結果を24時間として保持し、`24:00:00` と表示する。
時部分を24で剰余化して満タン前に `00:00:00` と表示してはならない。残り時間が
ちょうど1日以上になった場合は日表示へ切り替える。

秒表示を実際のカウントダウンとして機能させるため、ウィンドウ表示中の画面更新間隔を
30秒から1秒へ変更する。タスクトレイ格納中は従来どおり更新ループを停止し、再表示時に
現在時刻から即時再計算する。最大100ゲームを対象とした単純な算術計算だけなので、
バックグラウンド通知処理や保存処理を毎秒実行しない。

## 7. ゲーム別通知

### 7.1 実効状態

通知コーディネーターは、ゲームごとに次を評価する。

```text
isEffectiveNotificationEnabled =
    settings.NotificationsEnabled && game.IsNotificationEnabled
```

- SettingsがOFFの場合は、従来どおり本アプリの全予約を解除して抑止状態へ移す。
- SettingsがONかつ個別通知がOFFの場合は、そのゲームだけ既存予約を解除して抑止する。
- 個別通知をONへ戻した場合は、そのゲームだけ現在の全回復時刻から再評価する。
- 通知時刻を過ぎているが満タン前の場合などの挙動は、既存の通知状態機械に従う。
- 個別通知の変更、ゲーム追加・編集、バックアップ復元後は、既存の
  `GamesChanged` 経路から予約を再調整する。

通知サイクルキーは引き続き `GameId / FullAtUtc ticks / leadMinutes` で生成する。
回復秒は `FullAtUtc` に反映されるため、キー形式の変更は不要である。

通知OFFの判定は、通知サイクルや全回復時刻の生成より先に行う。現行の
`NotificationStateMachine.Evaluate` は時刻生成時の `InvalidSchedule` を先に返すため、
単に実効状態を引数へ渡すだけではならない。通知無効時の優先分岐では次を行う。

- Windowsに既存予約があれば、計算可能性に関係なく `Cancel` を返す。
- 予約解除の判断後、通知サイクルを計算できる場合は、既存台帳の有無にかかわらず
  現在サイクルを `Suppressed` として保存する。
- 通知サイクルを計算できず、既存台帳が `Scheduled` の場合は、その既存エントリを
  `Suppressed` へ遷移させる。
- 既存予約がなければプラットフォーム操作は行わないが、計算可能な抑止サイクルの
  台帳保存は省略しない。
- OFF処理では `InvalidSchedule` を理由に予約を保持しない。

これにより、`Settings ON + 個別通知OFF + 計算不能 + 既存予約あり` の場合も、古い
Windows予約を必ず解除する。また、新規ゲームを個別OFFで保存した場合もOFF期間中の
サイクルを記録する。再びONにした時点で通常の時刻生成と妥当性検証を行い、通知時刻を
過ぎた `Suppressed` サイクルは即時通知せず `Consumed` へ移す。

### 7.2 バックアップ

個別通知はゲーム設定の一部としてユーザーバックアップへ含める。通知台帳は従来どおり
端末固有データとしてバックアップへ含めない。復元後は、復元された個別通知と現在の
Settingsマスター設定から端末側の予約を再構築する。

## 8. 外観切替クラッシュの原因と対策

### 8.1 再現結果

次の操作でクラッシュを再現した。

1. Settingsでテーマまたはバックドロップを変更する。
2. Overviewへ戻る。
3. Settingsへ入り直す。
4. テーマとバックドロップを再度変更する。

元ログと再現ログはいずれも `Microsoft.UI.Xaml.dll` の `E_INVALIDARG` で終了した。
再現ログではその前に `0x8001010D` が記録された。現行コードでは、`Toggled` と
`SelectionChanged` の入力イベント中に、次のCOM/XAML処理が同期実行されている。

- ルートの `RequestedTheme` 変更。
- `Window.SystemBackdrop` の差し替え。
- `ActualThemeChanged` からの `AppWindow.TitleBar` 色変更。

設定ViewModelのセマフォは複数変更を直列化するが、最初の変更は待機せず入力イベント中に
実行されるため、入力同期COM呼び出しを防げない。

### 8.2 適用キュー

テーマとバックドロップのUIイベントは、設定変更を `DispatcherQueue` の次のターンへ
明示的に送ってから実行する。これにより、ToggleSwitchまたはComboBoxの入力同期処理を
終了した後でXAML/COMへ外観を適用する。

- キュー投入失敗は例外として既存のInfoBar経路へ報告する。
- ViewModelの `_mutationGate` は維持し、永続化、ロールバック、外観適用の順序を保つ。
- Settingsから離れた後にキュー済み処理が完了しても、同じSettingsPageインスタンスと
  ViewModelへ結果を反映できる。
- 連続操作は直列処理し、最後に正常保存された選択値へコントロールを同期する。

キュー処理はテスト可能な小さな抽象へ分離する。実環境では
`DispatcherQueue.TryEnqueue` を使用し、単体テストでは投入成功・投入失敗・実行順を
制御できるフェイクを使用する。

### 8.3 タイトルバー色

`ActualThemeChanged` では `AppWindow.TitleBar` を直接変更しない。

- 色更新要求を `DispatcherQueue` へ送る。
- 未処理の更新がある場合は追加要求をまとめ、最新の `ActualTheme` を1回適用する。
- タイトルバー色は補助的な外観処理なので、想定可能なCOM、引数、ライフサイクル例外は
  診断出力へ記録し、ゲーム管理処理を終了させない。
- コンストラクターでの初期色適用と、ユーザーが追加したLight/Dark用配色は維持する。

タイトルバー色の集約状態もUIコントロールから分離してテスト可能にし、複数要求後に
1件だけキュー投入され、実行時点の最新テーマが適用されることを保証する。

### 8.4 バックドロップ

外観適用を入力イベントから分離した上で、既存の
`MicaBackdrop`、`DesktopAcrylicBackdrop`、WinUIExの `BlurredBackdrop`、
`TransparentTintBackdrop`、Solidを維持する。環境非対応、高コントラスト、透明効果OFF、
リモートセッション時のSolidフォールバックも変更しない。

## 9. エラー処理

- 回復間隔の不正値は保存前にフィールドエラーとして表示する。
- 既存データ移行に失敗した場合は破損扱いとし、回復用コピーを試す。
- 通知予約・解除の一部失敗は既存の結果型へ集約し、ゲームデータ保存を巻き戻さない。
- 外観設定の保存失敗では、従来どおり直前のテーマまたはバックドロップへ戻す。
- ネイティブのフェイルファストはcatchへ依存せず、入力同期COM呼び出しを避けることで
  防止する。

## 10. テスト戦略

### 10.1 単体テスト

- 1秒、59秒、1分、8分30秒、最大値の回復計算。
- 回復境界の直前・到達時・直後と、端末時計が過去へ変更された場合。
- 分・秒の各範囲、`0分0秒`、最大値超過、全回復時刻オーバーフロー。
- 回復秒変更時だけ `RecordedAtUtc` が更新されること。
- 個別通知変更だけでは `RecordedAtUtc` が変わらないこと。
- スキーマ1のJSONと既存バックアップが、0秒・個別通知ONとして読み込まれること。
- スキーマ2の保存・読込、未知スキーマ拒否、新必須項目の欠落拒否。
- プライマリのスキーマ2必須項目欠落時に、正常な回復用コピーへフォールバックすること。
- バックアップのマニフェストと内部データのスキーマ不一致を拒否すること。
- Settings ON/OFFと個別通知ON/OFFの4組合せ。
- 個別通知OFF時の予約解除、ONへ戻した場合の再予約。
- `Settings ON + 個別通知OFF + InvalidSchedule + 既存予約あり` でも解除すること。
- 台帳・Windows予約がない個別通知OFFゲームでも、計算可能な現在サイクルを
  `Suppressed` として保存すること。
- 個別OFF中に通知時刻を過ぎた後でONへ戻しても即時通知せず、`Consumed` へ移ること。
- 1日未満、1日境界、1日以上、満タンの残り時間分解。
- `23:59:59.x` が `24:00:00` となり、満タン前に `00:00:00` とならないこと。
- 画面更新間隔が1秒であること。
- 外観キューの投入失敗がInfoBar報告へ到達すること。
- 外観変更が投入順に直列実行され、最後に正常保存された値へ同期すること。
- タイトルバー色の複数更新要求が1件へ集約され、最新テーマを適用すること。

### 10.2 UI・統合テスト

- 編集ダイアログの分・秒入力、エラー、個別通知トグル、保存後の永続化。
- Overviewカードとコンパクト表示の `hh:mm:ss`。
- Settings通知OFFでは個別通知ONのゲームも予約されないこと。
- Settings通知ONでは個別通知ONのゲームだけ予約されること。
- `Settings → Overview → Settings` を含め、Light/Darkと5背景を複数周切り替える。
- 各外観切替後にプロセスが生存し、Settingsへ再入場でき、実際のバックドロップ診断が
  選択値と一致すること。
- Light/Dark、キーボードフォーカス、AutomationId、狭いダイアログ幅で視覚確認する。

## 11. 受け入れ条件

- 回復間隔を分＋秒で登録・編集でき、秒単位で現在スタミナと全回復時刻が計算される。
- 既存データと既存バックアップを失わず、既存ゲームの個別通知がONで移行される。
- Settingsの通知がONの場合に限り、個別通知ONのゲームだけが通知対象になる。
- 1日未満の残り時間が `hh:mm:ss` で毎秒更新される。
- 1日以上の表示は `D日 hh:mm` のままである。
- SettingsとOverviewを往復しながらテーマと5背景を反復変更してもクラッシュしない。
- ユーザーによる既存UI変更を保持し、全単体テスト、外観回帰UIテスト、通知統合テストが
  成功する。
