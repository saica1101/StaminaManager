# バックドロップ・ゲーム編集・設定表示改善 設計仕様

## 1. 文書の位置付け

本書は、既存の
`docs/superpowers/specs/2026-07-25-stamina-manager-design.md` および
`docs/superpowers/specs/2026-07-29-recovery-seconds-per-game-notifications-appearance-stability-design.md`
に対する追加仕様である。バックドロップ、ゲーム編集ダイアログ、画像容量、削除操作、
Settingsの表示文言について競合する場合は本書を優先する。

特に2026-07-29仕様の「Mica、Acrylic、Blur、Transparent、Solidの5背景を維持する」確定事項、
5背景の切替を求めるテスト戦略、5背景を維持する受け入れ条件は、本書の「Mica、Acrylic、
Solidの3背景」へすべて読み替える。

ユーザーが作業用worktreeへ加えた未コミットのUI調整は所有権を維持し、本変更で巻き戻さない。

## 2. 確定事項

- 選択可能なバックドロップは `Mica`、`Acrylic`、`Solid` の3種類とする。
- 旧設定に `Blur` または `Transparent` が保存されている場合は、`Acrylic` へ移行する。
- ゲーム追加・編集ダイアログは、呼び出し元のLight/Darkテーマを継承する。
- 回復間隔の分・秒入力の上へ「スタミナが1回復する時間」を表示する。
- ゲーム画像に対するアプリ独自の5MB容量制限を撤廃する。
- ゲーム編集と削除確認の削除ボタンは、Fluent Designに沿った赤い破壊的操作として表示する。
- Settingsのセクション名とバックアップ操作名を指定された日本語へ変更する。

## 3. バックドロップ

### 3.1 選択肢と対応付け

Settingsの選択肢を次の順で表示する。

1. Mica
2. Acrylic
3. Solid

ComboBoxのインデックスを `BackdropKind` へ直接キャストしない。表示インデックスと
`BackdropKind` の対応は、許可された値だけを持つ明示的な対応表または選択項目モデルへ
集約する。これにより、互換用enum値の有無や並び順がUI選択へ影響しないようにする。

### 3.2 旧設定の移行

既存JSONを読み取れるよう、`Blur` と `Transparent` の識別値は互換用として保持してよい。
ただし、設定読込後かつ外観適用前に次の正規化を必ず行う。

```text
Blur        -> Acrylic
Transparent -> Acrylic
```

プライマリ、回復用コピー、バックアップに含まれるschema 1/2のデータは、共有のデータ
コーデックで同じ規則により正規化する。`Blur` と `Transparent` だけを `Acrylic` へ写像し、
未知の数値または未知のenum値は破損データとして拒否する。

通常起動では、外観適用前のメモリ上の値を必ず `Acrylic` にする。その後、既存の原子的な
データ保存経路で正規化済み設定を書き戻す。書戻しに失敗した場合は旧ファイルを変更せず、
メモリ上の `Acrylic` で起動を継続して警告を報告する。次回起動または次に成功した設定保存で
再度正規化済みデータの永続化を試みる。バックアップ復元では、正規化済みのステージデータを
既存トランザクションでコミットし、失敗時は従来どおり復元前データへロールバックする。

UIだけでなく、外観サービスの適用境界でも `Blur` と `Transparent` を `Acrylic` へ
フォールバックし、旧値がWinUIExのBlurまたはTransparent実装へ到達しないようにする。
未知値は適用せずエラーとして扱い、破損を隠さない。

現時点では互換用クラスやソースファイルを物理削除せず、未使用状態とする。不要ファイルの
削除は別途、対象を明示して確認を得た場合だけ行う。

### 3.3 既存のクラッシュ対策

外観変更のDispatcherQueueへの遅延、変更の直列化、タイトルバー色更新の集約、環境非対応時の
Solidフォールバックは維持する。旧値の移行後も、Mica・Acrylic・Solid間の反復切替と
`Settings → Overview → Settings` の往復でクラッシュしないことを確認する。

## 4. ゲーム追加・編集ダイアログ

### 4.1 テーマ

ダイアログ生成時に、呼び出し元ページの実際のテーマを `RequestedTheme` へ設定する。
作業用worktreeに既に存在する `RequestedTheme = ActualTheme` を採用し、削除または別方式へ
置き換えない。追加時と編集時の両方が同じ生成経路を通ることをテストで保証する。

削除確認は別の `ContentDialog` を生成せず、同じ `GameEditorDialog` が
`DeleteConfirmation` 状態へ切り替わる現行構成を維持する。したがってテーマと `XamlRoot` は
編集状態と削除確認状態で同一のものを継続使用する。

### 4.2 回復時間ラベル

分・秒の入力グループの直前へ「スタミナが1回復する時間」を表示する。既に加えられている
ユーザー変更を維持し、ラベル、分入力、秒入力、エラー表示が狭い幅でも切れないよう、
行の高さはコンテンツに追従させる。

### 4.3 画像容量

通常の画像選択・保存、およびバックアップからの画像復元について、画像1件あたり5MBという
アプリ独自の上限を撤廃する。読込処理は固定長の5MBバッファや上限超過例外を使用せず、
ストリームの実サイズを扱う。通常保存では入力全体を単一の `byte[]` に保持せず、ストリーム
または一時ファイルを使ってデコーダーへ渡し、ファイル容量と同量の不要なメモリ確保を避ける。

「容量上限なし」はアプリ独自のファイルサイズ制限を設けないことを意味する。次の既存の
安全策は維持する。

- 画像寸法の上限: 4096×4096。
- 対応形式と画像デコーダーによる妥当性検証。
- バックアップ全体のファイルサイズ、展開後サイズ、画像件数、圧縮率の上限。
- OS、ファイルシステム、利用可能メモリ、画像デコーダーに由来する実行環境上の制約。

バックアップ読込では、manifest、data、全画像で共有する `long` 型の実測展開予算を持つ。
各チャンクを読み出すたびに実測バイト数を加算し、`MaxExpandedBytes` を超える前に処理を中断
する。途中失敗とキャンセルでは、作成済みのステージファイルおよび一時ディレクトリを回収する。
エクスポートでも全画像の実サイズから全体上限を事前確認し、書込み中の実測サイズも検証する。
上限超過、I/O失敗、キャンセル時は未完成のバックアップ一時ファイルを回収する。

画面上の「5MB以下」という説明と、5MB超過を示すエラーメッセージを削除する。
バックアップ時だけ旧上限が残って大容量画像を再利用できなくなる状態を避ける。

## 5. 破壊的操作の表示

削除ボタン用に再利用可能なセマンティックスタイルを定義し、次の両方へ適用する。

- ゲーム追加・編集ダイアログの［削除］ボタン。
- 同じ `GameEditorDialog` の削除確認状態で生成される主ボタン。

スタイルはLight、Dark、高コントラストを考慮し、通常、ポインターオーバー、押下、無効、
フォーカスの各状態を識別できるようにする。色はWinUIのシステムCriticalリソースまたは
テーマ別のセマンティックリソースへ集約し、コントロールへ赤色を直接ハードコードしない。
文字色とのコントラストを確保し、色だけに依存せずボタン文言も「削除」とする。
共有スタイルは色と視覚状態だけを担当し、`AutomationId` と `AutomationName` は編集状態の
削除要求ボタンと削除確認状態の主ボタンへそれぞれ固有に設定する。

確認ダイアログの既定ボタンはキャンセル側のままとし、Enterキーだけで誤削除されない
既存の安全性を維持する。

## 6. Settingsの表示文言

次の表示へ変更する。

| 変更前 | 変更後 |
|---|---|
| Appearance | 外観 |
| General | 動作 |
| Notifications | 通知 |
| Data | バックアップ |
| バックアップを書き出す | エクスポート |
| バックアップから置き換える | インポート |

作業用worktreeの既存リソース変更を採用する。表示ラベルに加え、スクリーンリーダー向けの
AutomationNameや操作説明も新しい用語へ揃える。Resources.reswとXAMLを横断し、
`Appearance`、`General`、`Notifications`、単独見出しとしての `Data`、
「バックアップを書き出す」「バックアップから置き換える」が対象UIの表示文言・操作名・
説明に残っていないことを検証する。

## 7. エラー処理

- 旧バックドロップ値は例外や起動失敗にせず `Acrylic` へ正規化する。原子的書戻しに失敗した
  場合は旧ファイルを保持し、メモリ上の正規化値で継続する。
- 画像の形式不正、寸法超過、デコード失敗、I/O失敗は従来どおりユーザーへ表示する。
- 画像選択のUI境界では `OutOfMemoryException` を明示的に捕捉し、選択中の画像を採用せず、
  作成済み一時ファイルを回収して「画像を処理するためのメモリが不足しています」と表示する。
  それより下位では広域catchで握りつぶさず上位へ伝播し、保存成功として扱わない。
- 外観設定の保存または適用に失敗した場合は、既存のロールバックとInfoBar報告を維持する。

## 8. テスト戦略

### 8.1 単体・契約テスト

- 選択インデックスからenum、enumから選択インデックスの双方が `Mica`、`Acrylic`、`Solid` の
  みに対応すること。範囲外インデックスを拒否し、正規化後の `Acrylic` がUIのAcrylic項目へ
  同期されること。ViewModelとイベントハンドラーの直接enumキャストを契約テストで禁止する。
- 旧 `Blur` と `Transparent` がそれぞれ `Acrylic` へ移行・保存されること。
- 旧値の原子的書戻しに失敗しても旧ファイルを保持し、メモリ上の `Acrylic` で起動すること。
- 未知のバックドロップ値は正規化せず破損として拒否すること。
- 外観サービスへ旧値が渡されてもWinUIEx Blur/Transparentを生成しないこと。
- 5MBを超える有効画像を通常保存できること。
- 5MBを超える有効画像を含むバックアップを読込・復元できること。
- 画像寸法上限とバックアップ全体の安全上限が引き続き機能すること。
- バックアップのメタデータ上の合計超過、ストリーム読込途中の実測合計超過を拒否し、
  上限超過とキャンセルのどちらでも一時ファイルを回収すること。
- ゲーム追加・編集ダイアログが呼び出し元テーマを要求すること。
- 両方の削除ボタンが同じ破壊的操作スタイルを参照すること。
- 指定したSettingsの表示・AutomationName・説明リソースが新しい日本語表記になり、旧語が
  対象UIへ残っていないこと。

### 8.2 ビルド・UI確認

- ソリューションの全テストとReleaseビルドを実行する。
- Light/Darkの各テーマで追加・編集・削除確認ダイアログを開き、背景と文字が一致すること。
- 削除ボタンの通常、ホバー、押下、キーボードフォーカスを確認する。
- Settingsのバックドロップに3項目だけ表示されること。
- `Mica → Acrylic → Solid` を複数周切り替え、Overviewとの往復後もプロセスが生存すること。
- 5MB超画像を選択し、保存後のOverview表示とバックアップ往復を確認する。

## 9. 受け入れ条件

- Settingsから `Blur` と `Transparent` を選択できず、旧設定は `Acrylic` へ安全に移行する。
- ゲーム追加・編集・削除確認ダイアログがアプリのLight/Darkテーマと一致する。
- 分・秒入力の上に「スタミナが1回復する時間」が表示される。
- アプリ独自の5MB画像上限が通常保存とバックアップの双方からなくなる。
- ゲーム編集と確認ダイアログの削除ボタンが、テーマ対応した赤い破壊的操作として表示される。
- Settingsの見出しとバックアップ操作が指定された日本語で表示される。
- ユーザーの既存変更を失わず、関連テストとビルドが成功する。
